## 4. Как работает система

**React** рисует страницы и хранит состояние интерфейса. **TypeScript** проверяет типы при сборке. **Express** принимает HTTP-запросы и выполняет проверки. **PostgreSQL** хранит данные. **Docker Compose** запускает приложение и БД вместе. **Caddy** даёт дополнительный HTTPS.

```text
Браузер: ID товара + количество + имя + ключ запроса
    -> POST /api/orders
    -> проверка данных и повторной отправки
    -> BEGIN
    -> цены и доступность из products
    -> INSERT в orders и order_items
    -> COMMIT
    -> номер заказа и секрет отслеживания
    -> браузер сохраняет квитанцию и показывает My orders
```

При ошибке выполняется ROLLBACK. Соединение с БД возвращается в пул в `finally`.

**Почему цена правильная:** браузер отправляет ID и количество. Сервер читает цену из БД и считает сумму. Переданный из браузера произвольный total не используется.

**Почему нет дубликата:** браузер сохраняет `Idempotency-Key`. Для повторного запроса с тем же содержимым сервер возвращает существующий заказ. Если с тем же ключом отправить другую корзину - 409. Advisory lock заставляет одновременные запросы с одним ключом ждать друг друга; уникальный индекс дополнительно защищает ключ.

**Почему недоступное нельзя заказать:** сервер читает только `active` товары. Для выбранных строк используется `FOR SHARE`: изменение цены/доступности ждёт завершения этой транзакции. Одна скрытая кнопка на сайте не была бы достаточной защитой.

Статусы: **New -> Preparing -> Ready -> Completed**. Cancelled разрешён из New или Preparing. Нельзя сразу перевести New в Completed. Проверка перехода входит в условие SQL UPDATE, поэтому два сотрудника не должны независимо применить несовместимые переходы к одному старому состоянию.

> The browser sends product IDs and quantities. The server reads prices from the database and calculates the total. The order and its items are saved in one transaction. If a step fails, the transaction is rolled back.

## 5. Ключи и доступ

| Механизм | Для кого | Зачем и где хранится |
|---|---|---|
| JWT | Сотрудник | Доступ к заказам, меню и аналитике. В браузере - sessionStorage; сервер проверяет подпись, срок и admin role. Срок - 8 часов |
| trackingToken / X-Order-Token | Клиент | Прочитать конкретный заказ. В localStorage вместе с номером; в БД хранится хеш |
| Idempotency-Key | Оформление | Повторная отправка не создаёт второй заказ. Ключ и fingerprint временно сохраняются в localStorage; сервер сохраняет request_key и request_hash |

Один номер заказа без trackingToken теперь не открывает заказ. 404 в таком запросе - ожидаемая защита.
Пароли сотрудников хешируются **bcrypt**. Хеш нельзя просто расшифровать обратно. Для tracking/request значений используется **SHA-256**. **JWT не шифрует все данные**; **HTTPS шифрует соединение**.

SQL использует параметры `$1`, `$2`, а не склеивание текста клиента с запросом. Это помогает защищаться от SQL injection.
Сервер также ограничивает размер JSON до 32 KB и число попыток входа - 15 за минуту на IP.

На компьютере клиента: корзина и квитанции в localStorage; JWT в sessionStorage. После очистки localStorage клиент теряет секреты своих заказов. Сами заказы остаются в PostgreSQL и доступны сотруднику. Это не аккаунт и не межустройственная история.

> Staff use an expiring JWT. Customers use a secret key to read their own order. A separate checkout key prevents duplicate orders. These keys have different purposes.

| Таблица | Что хранит | Что сказать |
|---|---|---|
| users | id, username, password_hash, role | Учётные записи сотрудников. Здесь нет регистраций клиентов |

В products категория - ограниченный текст: Burgers, Drinks, Desserts. Отдельной Categories-таблицы нет.

## 7. API и графики

**API** - интерфейс запросов между браузером и сервером. **JSON** - формат данных. **REST** - организация маршрутов вокруг ресурсов и HTTP-методов.

| Запрос | Что делает | Доступ |
|---|---|---|
| GET /api/health | Проверяет связь с БД | Публичный |
| GET /api/products | Доступное меню | Публичный |
| POST /api/orders | Сохраняет заказ | Публичный, с валидными данными и Idempotency-Key |
| GET /api/orders/:id | Читает заказ | Нужен X-Order-Token |
| POST /api/auth/login | Выдаёт JWT после входа | Логин/пароль |
| GET /api/orders | Список заказов с именами | JWT admin |
| POST /api/products; PUT /api/products/:id | Создание/редактирование товара | JWT admin |
| PATCH /api/orders/:id/status | Смена статуса | JWT admin |
| GET /api/analytics | Данные графиков и очередь | JWT admin |

Показать без секретов: открыть `http://localhost:4000/api/health` и `/api/products`. Для реального запроса сайта открыть DevTools -> Network -> Fetch/XHR -> действие -> Response. Не публиковать токены из Headers.

Коды: **200** успешно, **201** создано, **400** неверные данные, **401** нет действующего доступа сотрудника, **404** не найдено/нет ключа заказа, **409** конфликт, **429** слишком много попыток входа, **503** БД недоступна.

### Что делает GROUP BY

Объединяет строки с одинаковым значением признака в группы. SUM или COUNT считает результат внутри каждой группы. JOIN связывает строки разных таблиц. ORDER BY сортирует результат; GROUP BY сам по себе сортировку не обещает.

```sql
SELECT i.name, SUM(i.qty) AS quantity
FROM order_items i JOIN orders o ON o.id = i.order_id
WHERE o.status <> 'Cancelled'
GROUP BY i.name
ORDER BY quantity DESC
LIMIT 8;
```

Если Cheeseburger встречается в трёх позициях с qty 2, 1, 3, результат группы - **6 штук**, не 3 заказа.

| График | Расчёт | Почему такой вид |
|---|---|---|
| Популярные товары | SUM(qty) по имени, без Cancelled | Горизонтальные столбцы удобно сравнивать по длине |
| Выручка по дням | SUM(total) только Completed, группировка по дате | Линия показывает изменение во времени |
| Заказы по часам | COUNT(*) по часу создания | Столбцы показывают распределение запросов; отменённые тоже считаются |

Часы/даты SQL переводит в `Asia/Qyzylorda`. Период истории и фильтры берите из текущего запроса. Это не прогноз.
В начале загружены **120 синтетических заказов**, `is_demo=true`. Проверки добавляют новые записи. Число в Insights не обязано остаться 120. Графики показывают расчёты, а не реальные продажи кафе.
Все три запроса: `docs/ANALYSIS.sql`. Запустить из обычного терминала:

```sh
docker compose exec -T db psql -U cafe -d cafe < docs/ANALYSIS.sql
```

> GROUP BY collects rows with the same product name. SUM adds their quantities. We exclude cancelled orders from product popularity and completed revenue uses only Completed orders. The dataset is synthetic.

### Картинки и доступность

- Растровые фото: WebP, обычно 400 и 800 px; Cheeseburger имеет вариант 740 px. `srcSet` помогает выбрать размер.
- `loading="lazy"` откладывает загрузку непервых фото; главная картинка загружается раньше.
- `width`/`height` резервируют место; `alt` описывает фото для экранного диктора.
- SVG - логотип и иконки, остаются чёткими при увеличении.
- JPEG/WebP обычно используют сжатие с потерями; PNG - без потерь. MP4 - контейнер, H.264 - видеокодек.
- Названия кнопок, видимый фокус, ошибки у поля, сообщение после добавления и reduced motion помогают пользоваться интерфейсом.
- Фото и лицензии: `web/public/media/provenance.json` и `credits.html`.
- Наличие аудиофайла в папке не означает, что сайт его проигрывает. Резервное видео без звука; выступаете вы.

> We use smaller WebP photos to reduce download size. The browser can choose a suitable image size. Alternative text describes the image. SVG keeps logos and icons sharp.

### Smart и IoT

```text
estimated wait = min(60, 5 + 3 × active orders) минут
active = New + Preparing
```

0 активных -> 5 минут; 3 -> 14 минут; 20 -> 60 минут из-за ограничения. Обновление Insights - 8 секунд.
Это программное правило на заказах. **Нет физического датчика, обученного ИИ и проверенного прогноза кухни.**
Предложение на будущее: анонимный счётчик людей у выдачи -> Wi-Fi/HTTPS -> API -> таблица измерений -> предупреждение сотруднику. Этот маршрут и оборудование ещё не реализованы.

> The current smart feature is a simple rule based on active orders. It is not a physical IoT system. We have not compared the estimate with real kitchen times.

## 11. Команды Git

Из корня проекта:

```sh
git log --oneline --graph HEAD
git show --stat 68d3409
git show 68d3409 -- web/src/media.tsx
git show 2eeca81 -- server/schema.sql
git show b11a34e -- tools/final-checks.mjs
git status --short
```

В diff `+` - добавлено, `-` - удалено. `git show --stat` показывает затронутые файлы; следующая команда - конкретный diff.
Для merge: `git diff c1102c5^1 c1102c5 --stat` показывает разницу с первым родителем.

Git: commit сохраняет снимок локально; push отправляет коммиты; fetch скачивает сведения об удалённой истории; merge объединяет ветки. Изменённый файл без commit не появляется на GitHub после обычного push.

Ответ про свой коммит строить так: **проблема -> файл -> изменение -> проверка**.

> The problem was that customers could send the same order again after a lost response. This code keeps one checkout key. The server returns the existing order for a retry. We tested five concurrent requests and checked that only one order was created.
